# MCP OAuth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add OAuth login for ChatGPT and Codex MCP connections, with each OAuth grant constrained by a selected Mailstack User-Token.

**Architecture:** Add an OAuth authorization server to the existing Express service, backed by versioned SQLite storage. The OAuth browser flow uses the existing Mailstack login, then requires explicit selection of one active User-Token. OAuth access tokens resolve to the current permission set of that parent token, intersected with the grant's scopes; existing direct User-Tokens remain supported.

**Tech Stack:** Node.js 20+, TypeScript, Express 5, SQLite via better-sqlite3, existing crypto helpers, EJS, MCP SDK, OpenAI plugin manifests.

**Spec:** `docs/superpowers/specs/2026-10-15-mcp-oauth-design.md`

## Global Constraints

- Use Authorization Code with PKCE `S256`; do not support implicit or password grants.
- Store only hashes of OAuth authorization codes and access tokens.
- OAuth scopes can narrow selected User-Token permissions, never expand them.
- Check parent-token status and current permissions on every MCP request.
- Keep management static tokens distinct from MCP credentials.
- Keep direct User-Token authentication working.
- Do not add refresh tokens in this release.
- Keep all OAuth browser redirects bound to registered exact redirect URIs.
- Keep public OAuth discovery and protected-resource metadata free of account and credential data.
- Do not log secrets, authorization codes, access tokens, or complete User-Tokens.
- Preserve IMAP and SMTP TLS certificate verification.
- The current package has no test script or test suite; do not add or run tests. Use the existing typecheck and code review for verification.

## Review Focus

- An authorization code is redeemed twice or with a wrong PKCE verifier: it must fail and never issue a second token (authorization-code storage/exchange).
- A callback URI differs by path, port, or query: authorization must reject it without redirecting to the unregistered location (client registration/authorization routes).
- A client requests a tool scope disabled on the selected User-Token: the scope must not be granted and that tool must remain unavailable (consent and principal resolution).
- The selected User-Token is revoked or loses a permission after OAuth grant: the next MCP request must reflect that change (repository and MCP middleware).
- An account already has a management session, or signs in through email-code login, during an OAuth flow: the authorization transaction must resume only for the session's verified account (login handoff routes).

**Interfaces:**

- [x] **Step 3: Implement authorization request creation and binding** to client ID, redirect URI, resource, state, PKCE challenge, requested scopes, and expiry. Persist only a hash of the browser transaction identifier and authorization code.
- [x] **Step 4: Implement code exchange** with `S256` verifier checking, exact client/redirect/resource matching, atomic one-time consumption, short-lived opaque access-token issuance, and no refresh token.
- [x] **Step 5: Return standards-compatible OAuth errors** for invalid clients, redirects, request fields, code, verifier, resource, and expired/reused authorization transactions without leaking stored identifiers.
